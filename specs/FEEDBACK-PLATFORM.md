# Feedback for the Vaadin teams: older than 25.4

Findings that reproduce on 25.3 or earlier, kept apart from `FEEDBACK-25.4.md` because a release team reads its own list. Same row format, same pipeline through `specs/issues/`, same rule: mark fixed, never delete.

| Finding | Expected | What happened | What we did instead | Where the workaround lives |
| --- | --- | --- | --- | --- |
| Breadcrumbs in `ROUTER` mode cannot carry an item that is not a route. Since 25.2 | A way to put a fixed leading item, such as a brand link to an external site, in front of the trail the router resolves | `ROUTER` mode throws `IllegalStateException` on any `add`, so one external root item forces `MANUAL` mode and with it a hand written copy of what `ROUTER` mode does: the hierarchy walk, the title resolution and the leaf without a path | `MANUAL` mode rebuilt in a `Signal.effect` over `UI.routerStateSignal()`, from `RouteConfiguration.getRouteHierarchy` and `Router.resolvePageTitle` | `base/ui/CustomerLayout.java`, `showTrail`. Draft `issues/01-breadcrumbs-leading-item.md`, ready |
| **Withdrawn, documented.** The built in `RouteNotFoundError` is rendered outside the `@Layout` automatic layout | An unknown address renders inside the application shell | Error views are not routes, so the automatic layout does not apply, and `building-apps/ui-basics/handle-errors` says so and names the fix | A subclass of `RouteNotFoundError` carrying `@ParentLayout`, which is the documented way and not a workaround. What stays ours is the trail: an error view is not a registered route, so the app bar resolves the root route by hand to offer a link home | `base/ui/NotFoundView.java`, and the not registered branch of `showTrail` in `base/ui/AppBar.java`. Epitaph in `issues/02-notfound-outside-layout.md` |
| A stylesheet that is not named `styles.css` is not served by a secured application. Known: flow#25576 from the 25.3 hackathon, open | The configurer permits what the application shell loads, including what those files import, or the styling page says where sheets must live | Corrected by the reproducer: it is not only imports. The default rule is deny all with a fixed public list, `/styles.css`, `/themes/**`, `/assets/**` and a few more, so any other sheet is refused, declared or imported, anonymous or signed in. Ours looked half working only because the entry sheet has the one public name. Nothing fails on the server and the page simply loses its styles | The partials live in `/styles/` and that path is permitted by hand in front of the configurer | `base/security/SecurityConfig.java`, `META-INF/resources/styles/`. Comment drafted in `issues/03b-comment-on-flow-25576.md`, ready |
| **Withdrawn, documented.** Signed in without the role, the refusal of a route reads as a missing page | One way to tell a signed in user "you are signed in but not allowed here" | A deliberate precaution, so the message does not reveal whether the view exists: `flow/security/access-control/error-views`. The same page shows the custom view for `AccessDeniedException` that an application adds when it wants to say so | Nothing yet. The custom access denied view is the documented way and is open as a decision | `ShellSecurityBrowserlessTest.guest_is_refused_on_findings` proves the refusal. Epitaph in `issues/04-role-refusal-reads-as-not-found.md` |
| The bootstrap page is served without the headers Spring Security writes | A policy configured through `http.headers().contentSecurityPolicy(...)` reaches every response | Every response carries it except the bootstrap page, in both modes: no `Content-Security-Policy`, no `X-Content-Type-Options`, and `X-Frame-Options` is `SAMEORIGIN` where Spring Security says `DENY`. Our browser test saw it only in the full `-Pit` run, which is the one that runs in production mode | The same policy is set again from an `IndexHtmlRequestListener` | `base/security/CspOnBootstrapPage.java`. Draft `issues/10-bootstrap-page-without-security-headers.md`, ready |
| With the default security rules an address that matches no route never reaches the not found view. Known: the open question at the end of the maintainer's answer on flow#25576 | Flow's not found view, as the feature document asks for a route that matches nothing | An anonymous request is redirected to the login page and a signed in one gets a bare 403 with an empty body, because every path that is not a view or on the public list is denied before Flow sees it. A browserless test cannot see this, it runs no filter chain | `anyRequest(rule -> rule.permitAll())` on the configurer, leaving the views to navigation access control. This gives up deny by default for anything that is not a view, and is open as a decision | `base/security/SecurityConfig.java`. Part of the comment in `issues/03b-comment-on-flow-25576.md` |
| `QueryParameters` does not keep the order of the parameters. Seen on 25.4.0-beta2, 25.3.5 and 24.9.26 | The order a query was built or parsed in is the order it is written back, so the address a view writes is the one its links show | `fromString`, the constructor with a `LinkedHashMap` and `Location` all write `boot=1&ruled=1&disc=1&open=x` back as `ruled=1&disc=1&boot=1&open=x`, so the address bar of the version screen reorders what the reader pasted on the first toggle | Our links write a fixed order, tests compare the query as a map. Draft `14-query-parameters-order.md` | `status/VersionAddress.java`, `VersionViewBrowserlessTest.assertAddress` |
| The error callback of the observed Clipboard API takes `PromiseAction.Error` from `com.vaadin.flow.component.trigger.internal`. Since 25.3 | Every type a public method takes is public API, documented in the javadoc | `ClipboardBinding.writeText(String, onCopied, onError)` and every other observed write and read take `SerializableConsumer<PromiseAction.Error>`. Naming the type, for one error handler shared by all copy buttons, needs an import from an internal package, and the type has no javadoc page. flow#26576 proposed moving it and was closed unmerged | A lambda at the call site, so the type is never named | `status/CveView.java`, `copyButton`. Draft `issues/15-clipboard-error-internal.md`, ready |
