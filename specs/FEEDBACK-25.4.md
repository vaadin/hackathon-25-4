# Feedback for the Vaadin teams: 25.4

Everything found while building this application on 25.4.0-beta2 that a Vaadin team could act on: an API that is missing, one that is awkward, one that is documented but absent, and every place where we had to write a workaround.

This file is part of the specifications on purpose. If this application is ever rebuilt from these specifications, whoever does it should hit none of this by surprise, and should check whether each entry is still true.

**How to add an entry.** One row per finding, in the table that matches its kind. Say what was expected, what happened, what we did instead, and where in this repository the workaround lives. If it is fixed later, do not delete the row: mark it fixed and in which version, because the code that works around it still has to be cleaned up.

**What happens to these.** Nothing goes straight from here to an issue tracker. The pipeline is `specs/issues/`: a draft per finding, a minimal reproducer per draft, a check against existing issues, and the posting script with its dry run. A row is a suspicion, a project is a fact. When an issue is opened, its link goes at the end of the row. A finding with no link is a finding nobody outside this repository has seen.

Routing, when drafting: an API on the server, a binder, a signal, the router goes to `vaadin/flow`. How a component behaves in the browser goes to `vaadin/web-components`. A Java component API and the AI family go to `vaadin/flow-components`. Browserless testing goes to `vaadin/browserless-test`. Something documented that does not exist goes to `vaadin/docs`, naming the page. A version or BOM problem, or a case where nobody can tell which module owns it, goes to `vaadin/platform`.

## CSP directives the components forced open

Per `specs/04-security.md`, every loosened directive is a fact the teams want, recorded the moment it happens.

| Directive | Forced by | Why |
| --- | --- | --- |
| `script-src 'unsafe-inline'` | Flow, the bootstrap page | The client engine is started by an inline script. The 25.4 strict mode replaces this with a nonce, in production mode only. Our own head script for the theme memory rides on the same permission |
| `script-src 'unsafe-eval'` | Flow, the client engine, and the development tools | JavaScript the server sends as a string is compiled in the browser. After moving our one string `executeJs` to `@JsDefinition`, the `warn` mode logs no call site of ours, so what still needs this is the framework and the dev server |
| `style-src 'unsafe-inline'` | The components | Style attributes and injected style elements. Vaadin's own strict policy keeps this one too |
| `img-src data:` and `font-src data:` | Aura and the components | Icons and fonts inlined as data URLs. Vaadin's own strict policy has the same two |
| Nothing loosened for uploads or the PDF Viewer | Epic 06, checked in `ScanUploadIT` and `TriageDownloadIT` in production mode and in a development run | The modular upload posts to `'self'`. The PDF Viewer fetches the document from `'self'` and runs pdf.js in a worker the policy's `script-src 'self'` already allows, since `worker-src` falls back to it. No violation was reported and the `warn` log named no call site |
| `form-action https://github.com` | The workbench's handover, epic 10 | Not forced by a component: the verdict leaves through a `NativeForm` GET into GitHub's new file editor, which `form-action 'self'` refuses. Only that origin is admitted, D-128, and `CspIT` proves another origin is still refused. A Vaadin application that hands data to another site through a form has to know this directive exists; nothing in the `NativeForm` javadoc mentions it |
| Nothing loosened for the AI components | Epic 11, checked in `AssistantPanelIT` in production mode and in development runs | The orchestrator streams over the existing push connection, the picture goes through the modular upload to `'self'`, the message list renders Markdown without inline script, and the Form AI field marker is driven through the 25.4 typed JavaScript, `executeJs(Class)`. No violation was reported and the `warn` log of the production run named no call site. The live model is reached from the server only, so `connect-src` stays `'self'` |

## Data needs toward cve-status

Not Vaadin findings: fields a screen needed that the published JSON does not carry, per `specs/02-data-source.md`. Each becomes an additive export in the cve-status pipeline, never a computation here. The first four rows came from the epics; the last four from the alignment with the prototype, where the prototype itself shows the datum or marks it missing. Two things the alignment found about the prototype that are neither a data need nor a Vaadin finding, how it counts a CycloneDX file and what its per row "not assessed" sentence counts, are observations about vaadin/cve-status in `REPORT.md`, not rows here.

| Screen | Field | Why nothing present covers it |
| --- | --- | --- |
| Explorer front door | The short product codes, `module_codes`, in `data/front.json` | The off only address grammar wants the written down codes, which today exist only inside the 66 MB `data.json` no session can fetch. Until the export lands the explorer addresses products by name, the source spec's own 6.2.6 fallback |
| Answer by CVE | An alias map, GHSA id to the tracked id, in `cases/index.json` or as `cases/cve/<alias>.json` redirects | An advisory is published under its tracked id only, and the catalogue in the index carries no aliases, so a pasted GHSA alias of a tracked CVE cannot be answered without fetching every advisory document. Until the export lands the screen answers it only when another asked id names it, D-62 |
| Advisories | A one line impact per advisory in the catalogue, `index.advisories` | Feature 07 asks for an impact column. The catalogue entry has none, only the few verdicts in `recent` carry an impact, and filling 535 rows would mean fetching 535 advisory documents. The column is left out, D-82 |
| Advisories | The date an advisory was published, in the catalogue | Rule 6.4.22 orders worst first, then oldest, then by id. With no date the list is ordered by severity and id, D-81. `cases/cases.json` already lists `advisory_published` as impossible |
| Customer shell | The reader's subscription, which the prototype's header shows as a chip "Enterprise" | The prototype writes that chip as a fixed word in its markup; no published document carries a customer's plan, and this application signs in no customer. The chip is left out, `specs/reviews/prototype/home.md`. It needs a source per reader, an account service rather than an export of cve-status |
| Answer by version | Whether a release changes the public API, per release or per upgrade target | The prototype draws a "No API changes" badge beside Same minor and marks it itself as measured by nothing: the measurements are about dependencies. The badge is left out, D-178, `specs/reviews/prototype/version.md` |
| Answer by version | The date each advisory was published, for the not assessed notice | The prototype writes "Published" there and marks the date as not carried; the version document and the index carry when the scan first saw an advisory, a different date. Nothing is drawn, D-179. The same field the catalogue's order needs, D-81, and the one the prototype's CVE screen marks missing after "First seen by our scans", `specs/reviews/prototype/cve.md` |
| Cases | Why each impossible case cannot be drawn, and what it would need, for every impossible case in `cases/cases.json` | The prototype prints both for its five impossible cases, but the sentences come from a table in its own code; the catalogue carries a `needs` for `fix_eta` alone and no why for any. The screen shows the published `needs` after "Would need:" and nothing else, D-195, `specs/reviews/prototype/cases.md` |
